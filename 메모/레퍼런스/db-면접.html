DB란 무엇인간요?

구조화한 데이터의 집합
dbms에서 주로 무결성 보장, 트랜잭션 관리, 빠른 조회 위한 인덱스, 장애에 대한 백업 등을 지원한다.

nosql(not only sql)이란?

비관계형 db를 말하는데, 보다 비관계적인 접근 방식을 제공해 덜 구조화된 동적 데이터를 다루기에 적합한 db종류입니다.

rdb처럼 데이터를 스키마에 맞춰 데이터를 저장하지 않고 문서, 키-값, 그래프 구조로 저장합니다.
엄격하게 구조화 되진 않았기에 데이터의 일관성을 맞추기 힘든 면이 있습니다.
하지만 유연하게 데이터들을 저장해 활용할 수 있고 데이터 삽입,조회 등의 작업성능이 좋은 편이며 scale in-out시에 유리합니다.

nosql이 적합한 상황은

  1. 엄밀한 데이터 정합성이 필요없을 때 (단순 저장,질의가 기능의 대부분일때)
  2. 서비스의 확장성이 더 중요하다고 판단할 때
  3. rdb가 제공하는 방식대로가 아니라 직접 데이터 관리를 하고 싶을때
    (데이터 관리계층을 어플리케이션 레벨에서 직접 제어)
    https://subokim.wordpress.com/2011/05/20/when-nosql-makes-better-sense/
  • 게임 적용 사례:듀량고
    nosql에 분산적으로 데이터를 저장하면
    서비스의 크기가 컴퓨터 노드의 용량에 구애받지 않는다. (게임 맵의 크기가 제한되지 않음)
    다만 여러 행동들에 대해 데이터 정합성을 맞추기가 어려울 수 있다.
    이를 버전 관리를 통한 제어, on-demand 마이그레이션, on-demand update, 서버 간의 통신 등으로 보완할 수 있다.
    오히려 로직을 복잡하게 만드는 것 아니냐는 단점도 있지만 확장성,모듈화의 장점이 더 크다고 판단하면 활용할 수 있겠다.
    https://www.slideshare.net/hoyoungchoi980/nosql-mmorpg

트랜잭션,잠금

이를 통해 동시성 제어/일관성,무결성을 보장할 수 있다.

트랜잭션이란 뭔가요?

원자적으로 성공,실패해야 하는 로직의 단위입니다.
이것이 원자적으로 관리되어야 데이터가 의도한대로 저장되어 정합성이 유지됩니다.
ACID하다는 특징이 있습니다.

  1. 원자성(Atomicity) 작업이 모두 반영되던지 아니면 전혀 반영되지 않아야 한다.
  2. 일관성(Consistency) 실행이 완료되면 언제나 일관성 있는 상태를 유지해야 한다.
  3. 독립성(Isolation) 둘 이상 트랜잭션이 동시에 실행될 경우 서로의 연산에 끼어들 수 없다.
  4. 영속성(Durability) 완료된 결과는 영구적으로 반영되어야 한다.

데이터의 정합성을 맞춘다는 게 무슨말인가요?

데이터끼리의 모순이 없다 - 데이터끼리 가리키는 사실이 일관적이라는 걸 의미합니다.

예를 들어 고객정보 테이블에서는 계좌가 3개라고 저장하는데,
고객의 예금 정보에는 5개의 계좌가 참조되어있다면 정합성이 맞지 않습니다.
모순이 없게 트랜잭션,배치 작업 등을 통해 관리합니다.

성능 상의 이점을 위해 일시적으로 정합성이 어긋나는 걸 허용할 수도 있습니다.

트랜잭션 격리의 수준은 어떤 것들이 있나요?

  • read uncommitted (dirty read 발생)
  • read committed (nonrepeatable read 발생)
  • repeatable read (phantom read, 갱신 유실이 발생할 수도 있음)
  • serializable

로 4가지가 있습니다.

read uncommitted는 트랜잭션을 거의 요청받은 순서대로 수행하게 되는데 이 과정에서 트랜잭션의 변경사항이 다른 트랜잭션에 제약없이 영향이 가게되어 문제가 발생할 수 있습니다.
(ex) 롤백되었는데도 그냥 이전의 데이터를 사용해서 작업 수행. 중간단계의 데이터를 완료된 데이터라 믿고 사용하게됨.)

read comitted는 타 트랜잭션에서 커밋된 데이터만 읽어오기에, 트랜잭션간 데이터 정합성이 상대적으로 맞습니다. 그럼에도 트랜잭션 진행시간 동안 다른 트랜잭션이 커밋하면
동일한 조회임에도 다른 데이터가 조회될 수 있습니다.

균형잡힌 격리수준이라 할 수 있는 repeatable read입니다.
다른 트랜잭션에서 커밋된 것만 읽으면서도 해당 트랜잭션내에서 같은 데이터를 읽을 때에는 일관적으로 읽을 수 있게해줍니다.
트랜잭션내에서 통용되는 버전관리, 이후에 시작한 트랜잭션의 변경이 영향이 미치지 않게 하는 방식을 상요합니다.
그럼에도 결과가 없던 데이터가 조회되는 팬텀 read,
일부 트랜잭션의 update결과가 무시되는 갱신유실
등이 발생하는 상황도 있습니다.

seriazlable은 트랜잭션들을 순서대로 실행시켜 무결성을 보장하지만, 성능 상의 단점이 있습니다.

갱신 유실이 발생하는 상황?

거의 동시에 실행되는 타 트랜잭션의 write결과를 읽어오지 못하는 경우 둘 중 한 트랜잭션만의 갱신결과만 적용될 수 있다.

  • 두 트랜잭션의 read타이밍이 update전에 이뤄지게되면 미처 락이 걸리기전 이기에 일부 연산만 실행된 결과가 저장될 수 있습니다.

트랜잭션은 격리는 어떻게 구현되나요?

read comitted는 read uncomitted와 다르게 쓰기 시에 x락을 사용합니다.
repeatable read는 레코드의 여러 시점에서의 상태를 저장해두어(스냅샷을 저장) 트랜잭션마다 select 시 일정한 데이터를 읽게 해줍니다.
serializable에서는 읽기 시에 공유 락을 걸어서 쓰기 작업이 있는 트랜잭션은 순차적으로 수행되도록 보장합니다.

트랜잭션의 롤백, 복구는 어떻게 구현되나요?

갑자스러운 중단에도 원자적으로 실행/실패되도록 만들어야 합니다.
이를 위해 여러 로그데이터를 이용합니다.
redo 로그,undo로그, commit로그를 이용해 롤백,장애복구를 합니다.

트랜잭션이 실패하면 버퍼풀의 내용을 undo로그의 내용으로 교체, undo로그 삭제.

undo?

트랜잭션 수행 과정에서 버퍼풀,디스크의 페이지를 수정하게 되는데 장애발생 등의 이유로 이 트랜잭션이 중간종료된다면 이 내용은 이전상태로 복구되어야 한다.
이 복구를 undo라 한다. undo로그에는 이전 버전의 데이터가 저장된다.

dbms는 보통 디스크와 디스크의 데이터를 페이지 단위로 캐싱하는 페이지 버퍼가 존재한다.

로그의 저장시점? - wal(write ahead logging)과 commit로그,체크 포인트

결국 장애는 어느시점에 발생하는지 예측할 수 없을텐데
undo로그를 어느시점에 저장하길래 이를 통해 복구할 수 있다는 걸까?

wal방식을 사용해 디스크의 수정 전에 먼저 로그를 작성하고, 트랜잭션 종료 후에는 commit로그를 작성한다.
복구 시에 해당 트랜잭션의 commit로그가 존재하면 undo로그로 복구를 할 필요가 없고,
commit로그가 존재하지 않는다면 undo로그로 복구한다.

그럼에도 절묘한 타이밍에 장애가 발생한다면 복구가 힘들 수도 있지 않을까?
트랜잭션을 디스크에 반영은 했지만 commit로그는 저장하기 직전의 절묘한 타이밍에 장애가 발생할 수도 있다.
dbms는 일정한 주기로 체크 포인트를 만들어 디스크의 상태에 대한 메타정보를 디스크에 저장하는데, 이 체크포인트와 redo 로그, commit로그 등을 이용해 복구를 해낼 수 있다.

트랜잭션의 커밋이란 뭔가요?

트랜잭션에서의 변경사항을 버퍼풀/디스크에 반영하고,
commit로그파일을 저장하고,
락을 해제하는 작업을 의미합니다.

mysql 갭 락이란 뭔가요?

키값 사이의 아직 존재하지 않는 데이터에 대해서도 잠금을 건다.

  • repeatable read수준에서 아래처럼 1-3사이에 락을 건다면 레코드 1과3, 그리고 그 사이의 2까지 공유락이 걸린다.

이를 통해 팬텀 리드를 막을 수 있다.
또한 바이너리 로그를 통한 replication과정에서 sql이 본래 db에서와 다른 순서로 sql을 실행하여 Source와 Replica간의 데이터 부정합이 생기는 걸 막아준다.

mysql에서의 mvcc란 뭔가요?

https://dev.mysql.com/doc/refman/8.0/en/innodb-multi-versioning.html
mvcc란 multi-version-concurrency-control의 약자로,
레코드 데이터의 변경 사항을 추적하며 여러 버전의 데이터를 유지해 저장해 여러 트랜잭션이 동시에 일정하게 데이터를 읽고, 쓰는 걸 가능하게 합니다.

트랜잭션이 데이터를 읽을 때 버퍼풀 or undo로그의 데이터를 읽습니다.
트랜잭션의 격리수준이 repeatable read라면 버퍼풀로부터 데이터를 읽은 후, 시작시점과 비교해 변경이 일어난 데이터라면 undo로그의 데이터를 읽습니다.
read comitted라면 버퍼풀로부터 최신의 데이터를 읽습니다.

즉 버퍼풀, undo로부터 필요한 버전의 데이터를 읽음으로써 일정한 읽기와 병렬적 실행을 가능하게 하는 버전제어 방식입니다.

트랜잭션을 짧게 유지하면 좋은 이유?

  1. 귀중한 커넥션을 계속 점유하고 있으면 안되기 때문에
  2. undo로그에 트랜잭션 동안의 변경 전 데이터가 쌓이기에 메모리 점유

동시성을 해결하는 방법들로 무엇들이 있나요?

낙관적,비관적 락
분산락 등을 활용할 있습니다.
예를 들어 은행에서 하나의 db를 사용한다면, 비관적 락을 걸어서
읽기 작업부터 x락으로 제한해 트랜잭션의 순서를 보장합니다.

이보다 성능,병렬성을 올릴 필요가 있다면
1차적으로 쓰기 작업에 대해서는 어플리케이션 단에서 분산락을 사용해서 트랜잭션을 격리하고 그럼에도 db에서의 동시 수정이 일어날 것을 염려해 낙관적 락을 거는 방법이 있겠습니다.

db파일

mysql의 데이터들은 어떤 형식으로 저장이 돼?

.ibd라는 파일 형식으로 저장됩니다.
메모장으로 열면 아래와 같이 보이는데, 결국 파일의 형태로 데이터행들을 저장합니다.

이를 이용해 데이터 복구 작업을 하기도 합니다.

redo로그 파일이란?

데이터 변경 시점마다 디스크까지 접근해 수정하는 것은 성능 상 비효율이 있습니다. 때문에 보통 버퍼 풀에 디스크의 수정된 페이지를 캐싱해 빠르게 저장,조회하게 만듭니다.
하지만 이 버퍼풀의 내용이 디스크에 반영되기 전에 db에 shot-down될 수 있으므로
데이터 변경 시 redo 로그파일을 만들어 버퍼풀-디스크의 싱크를 맞출 수 있도록 대비합니다.

mysql의 바이너리 로그와 redo로그 차이?

바이너리 로그는 모든 데이터 변경 sql문을 저장합니다.
redo로그는 데이터 변경 사항을 저장하지만 sql형태가 아니라 변경 이전-이후의 바이트 데이터를 저장합니다.
또한 redo로그는 스토리지 엔진단에서의 로그라는 점이 차이가 있습니다.

undo로그 파일이란?

트랜잭션 수행 전으로 복구하기 위한 정보를 담은 로그를 말합니다.
wal을 방식에서는 트랜잭션 수행 전에 기록되기도 하며,
롤백, 장애복구 시에 이 로그대로 복구를 수행합니다.

인덱스

인덱스란 뭔가요?

빠르게 원하는 정보를 검색하기 위해 테이블 또는 뷰와 연결된 디스크 내의 구조입니다.
데이터를 일정한 순서로 정렬하거나, 데이터의 위치를 따로 기록해서 그것을 참고해 조회합니다.

보통 사전에서 단어를 빠르게 찾기 위한 색인을 예시로 듭니다.
ex) 단어를 일정한 순서대로 정렬해 놓은 것.
사전의 뒤쪽에 단어가 존재하는 페이지를 기록해놓은 것

과 같이
db에서 데이터 행을 정렬하는 기준이 되는 키, 데이터에 빨리 접근하기 위한 메타데이터 구조를 의미합니다.

클러스터드 인덱스,넌클러스터드 인덱스(세컨더리 인덱스)가 뭔가요?

클러스터드 인덱스는 데이터 행을 정렬하는 기준이 되는 데이터입니다.
넌클러스터드 인덱스는 데이터 행과 별개로 메타 데이터를 저장한 것을 의미합니다.

클러스터드 인덱스로 보통 pk가 사용되는데, pk순서대로 정렬(정확히는 b tree의 형태로 순서대로 정렬)되어 디스크에 데이터가 저장됩니다. 정렬기준이 하나이어야 하기에, 클러스터 인덱스 또한 테이블 당 하나만 설정가능합니다.

넌클러스터드 인덱스는 클러스터 인덱스와 달리 별도의 인덱스 페이지를 만들어 저장합니다.
(별도의 메타데이터를 저장)
아래처럼 지정할 수 있고, 한 테이블에 여러개의 인덱스를 지정할 수도 있습니다.(그 경우의 단점도 있습니다.)

클러스터드 인덱스와 다르게 데이터의 위치를 찾은 후, 해당 위치로 접근하여 실제 데이터를 찾아오는 작업이 더 필요해 성능 상의 차이가 있을 수 있습니다.

인덱스를 사용한 경험을 알려주세요

인덱스의 단점은?

데이터의 수정,삭제,추가 시에 인덱스 또한 수정되어야 합니다.
즉 데이터 변경의 성능을 줄이는 대신 데이터 조회의 성능을 올리는 트레이드 오프 관계입니다.
때문에 잦은 변경이 일어나는 데이터에 대해서는 인덱스 적용을 지양합니다.

인덱스 사용 시의 주의점?

https://dev.mysql.com/doc/refman/8.0/en/optimization-indexes.html

  • 불필요한 인덱스는 공간을 낭비하고 MySQL이 사용할 인덱스를 결정하는 데 시간을 낭비하게 됩니다.
    또한 각 인덱스는 데이터 변경 시 같이 업데이트되어야 하므로 삽입, 수정, 삭제 비용이 추가됩니다.
  • 클러스터링 인덱스의 경우 길이가 가능하면 짧은게 좋습니다.
    세컨더리 인덱스에는 클러스터드 인덱스 정보를 포함하기 때문에 클러스터드 인덱스 필드의 용량이 크다면 더 많은 메모리를 점유하게 됩니다.

인덱스를 걸만한 필드의 특징들?

  • 삽입,삭제,변경이 많지 않은 필드면 좋습니다.
  • 빈번하게 조회되지 않고, 시간이 좀 걸려도 되는 조회라면 굳이 걸지 않아도 좋습니다.
  • 가능하면 유니크해야(카디널리티가 높아야) 의미가 있습니다.
  • 커버링 인덱스가 되도록 할 수 있다면 고려할만 합니다.

b+tree, b tree가 뭔가요?

이진트리와 다르게
b tree는 한 노드에 여러 개의 데이터가 들어갈 수 있으며,
자식 노드를 여러개 가질 수 있는,
리프 노드끼리의 뎁스 차이가 2이상 날 수 없게 균형잡힌트리이다.
이런 트리 구조로 이진탐색의 이점처럼 데이터의 일부만으로 대소를 판단해 더 빠르게 원하는 데이터에 접근할 수 있다.

B+tree와 b tree 둘의 차이는
특정 키 값이 리프 노드와 부모 노드에 중복해서 존재할 수 있는가
이다
위의 PK인덱스 그림을 보면 리프 노드에도 key인 emp_no 4,5 / 11,12 가 존재하고 부모인 루트 노드에도 4,5,11,12가 존재한다. 때문에 b+tree이다.
.

DB차원에서 더 구체적으로 보자면 아래와 같다.

B- tree 인덱스라 불린 부분도 사실 B+ tree가 맞다. mysql은 인덱스 구조로 b+ tree만을 사용한다
세컨더리 인덱스와 클러스터드 인덱스 트리의 차이점은 리프노드의 데이터이다.

클러스터드 인덱스 트리의 브랜치 노드는 최종적으로 실제 레코드가 담긴 페이지를 참조하여 리프노드에 레코드 정보가 담긴다.
반면 세컨더리 인덱스 트리에 리프노드에는 클러스터드 인덱스 값(pk)가 담긴다.

lsm 트리란?

주로 nosql(ex)카산드라)과 같은 log structure 저장 구조에서의 인덱스입니다.
키-값을 키 순서대로 정렬한 sstable이라는 형태로 데이터를 저장하는 방법입니다.
메모리에도 정렬된 key-value캐시를 유지하면서 일정 주기로 디스크의 sstable에 추가되는데, sstable은 불변이기에 수정이 아니라 최신의 데이터만 유지하고 기존 데이터는 삭제(compaction)합니다. 이렇게 merge되기에 LSM(log-structured-merge)이라 합니다.
lsm 트리는 sstable이 트리의 형식으로 저장된 것입니다.

결국 lsm이란 결국 키-값 레코드를 디스크에도 정렬된 상태로 유지하는 것인데,
이 때문에 인덱스이기도 하지만 저장방식의 일종으로 보기도 합니다.

mysql과 오라클의 차이?

엔티티,관계

엔티티란?

속성을 가지는 명사를 말합니다.

약한 엔티티와 강한 엔티티란?

다른것에 종속적이면 약함, 독립적이면 강한 엔티티입니다.

정규화란?

데이터 릴레이션에서 잘못된 종속관계로 이상현상이 일어나거나, 공간을 효율적으로 쓰기 위해 정리하는 것을 말합니다.
데이터의 중복을 줄이고, 릴레이션을 필요한 만큼만 구성하도록 합니다.

이상현상이랑 데이터의 crud가 의도되로 되지 않는 현상을 말하는데,
의도하지 않은 데이터가 저장되거나,
기존 데이터의 영향으로 삭제가 되지 않는 현상 등을 말합니다.

1,2,3정규형

  • 1정규형 - 한 속성에 더이상 분해되지 않는 하나의 데이터씩만 저장.
    원자적인 데이터 단위로 저장해라
  • 2정규형 - 제1정규형이며 완전함수 종속적이어야 한다.
    기본키의 일부만으로 결정될 수 있는 컬럼은 분리하자. 기본키의 일부 종속관계를 끌어다 붙여놓지말고 작게 나눠라.
  • 3정규형: 2정규형이면서 이행적 종속성이 없어야 함.
    -> 불필요하게 이어지는 종속성이 없어야함.
    기본키가 아니더라도 이어지는 관계를 끌어다 한 테이블에 붙여놓지마라.
  • BCNF정규형
    다른 컬럼값에 대한 결정권자는 모두 후보키이어야 한다.
    한 방향으로 이어지는 이행종속이 아니어도 종속성을 만들지마라. 후보키만이 종속성을 가지게 해라.

종합적으로는 테이블 내에서 불필요한 종속성을 만들어 같이 수정해야 되게 만들지 마라. 종속성이 있어야 한다면 그 결정권자는 유니크해야 한다. -> 한 테이블 안에서 불필요한 종속성 없이 관계를 충분히 작은 테이블들로 나누어라.

필드와 레코드란?

필드는 테이블에서의 속성 이름입니다.
레코드는 이 속성들에 해당하는 실제 구체적인 데이터 를 말합니다. 테이블에 행의 구조로 저장되는 데이터입니다.
