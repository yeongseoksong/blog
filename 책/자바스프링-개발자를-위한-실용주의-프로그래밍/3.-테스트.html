3. 테스트

2025년 6월 11일13 min read

  • topic/software-design
  • topic/spring
  • concept/testing
  • 한번 만들어진 테스트는 줄어들지 않고 늘어나기만 한다. 그래서 수동 테스트는 매번 같은 테스트를 반복해야한다.
  • 한번 만들어진 테스트는 줄어들지 않고 늘어나기만 한다. 그래서 수동 테스트는 매번 같은 테스트를 반복해야한다.
  • 테스트 코드
    • 어떤 메서드가 제대로 동작 하는지 확인
    • 어떤 서비스나 객체의 능동적인 행동의 결과 확인
  • 한번 작성된 테스트 코드는 시스템에 남아 코드가 변경될 때 마다 테스트하려는 대상이 초기 설계 의도를 벗어나지 않게 한다.
  • Regression : 시스템에서 정상적으로 제공하던 기능이 어떤 배포 시점을 기준으로 제대로 동작하지 않게 되는 상황 -> 회귀 버그란 의미이다.
  • 회귀 버그를 방지 하기 위해서는 해당 기능이 설계 의도와 알맞는지 능동적으로 감시가 필요하다. 이럴 때 버그를 탐지하고자 작성하는 테스트를 회귀 테스트 라한다.
  • 테스트를 통해 객체에 할당된 책임과 의도를 기술할 수 있다.
  • 테스트는 책임에 대한 계약이며, 문서 처럼도 사용될 수 있다.
    • 계약 : 테스트는 계약서를 구성하는 각종 조항과 같다. 한번 성사된 계약은 매번 같은 방식으로 객체에 할당된 책임을 감시할 수 있다.
    • 문서 : 테스트 코드는 객체의 책임을 드러냄과 동시에 책임을 실행하려면 어떤 입력을 줘야하는지 알려줄 수 있는 수단이다.
  • 테스트 피라미드 (위로 갈 수록 실 사용자와 가까운 테스트)
    • e2e 테스트 : api 테스트라고도 한다. 실제 사용자 시나리오에서 시스템이 어떻게 동작하는지를 검증하는 테스트
    • 통합 테스트 : 여러 컴포넌트나 객체가 협력해야하는 상황, 비즈니스 프로세스의 흐름을 검사하는 테스트
    • 단위 테스트 : 메서드, 클래스 같은 작은 코드 대상
  • 테스트 피라미드는 단위 테스트가 가장 많이, 먼저 작성되어야함을 알려준다.
  • 구글 테스트 피라미드
멀티 스테드멀티 프로세스멀티 서버
소형 테스트xxx
중형 테스트oox
대형 테스트ooo
  • 좋은 테스트는 결정적이고, 빨라야한다.
    • 결정적
      • 결정적(일관성 있는) 테스트는 좋은 테스트이다.
      • h2 연동을 하는 데이터 베이스는 비결정적으로 동작할 가능성이 있는 테스트 코드다.
      • 비결정적 테스트는 테스트 신뢰도를 떨어뜨리며 실패 상황 재현도 어렵다.
    • 속도
      • 느린테스트는 매번 실행하기 부담스럽다.
      • spring 컨테이너가 컨테이너를 초기화 하는 시간, h2 가 구동되거나 종료되는 시간이 테스트 속도에 큰 영향을 준다.
  • 소형 테스트는 비결정적이고 빠르다. 또한 모든 테스트를 병렬로 실행할 수 있다. 테스트의 분류중 가장 좋은 테스트이다.
  • 서비스 로직을 도메인에 위치 시켜 테스트를 소형 테스트로 쉽게 만들 수 있다.
  • 소형, 중형, 대형 테스트는 어떤 컴포넌트를 테스트 하느냐에 따라 결정되는 것이아니다.
    • 서비스, 컨트롤러 컴포넌트도 소형 테스트로 만들 수 있는데, 테스트 대역 을 사용하면 된다.
  • 테스트 대역(代役) : 테스트를 대신하는 가짜 객체나 컴포넌트를 의미
  • 테스트 대역을 사용해 테스트를 위한 격리되고 고정된 환경을 만들 수 있다. 즉, 예측할 수 있는 테스트 환경을 만들 수 있다.
테스트 대역 유형설명
dummy아무런 동작하지 않음
stub지정한 값만 반환
fake자체적인 로직 존재
mock아무런 동작하지 않으며, 어떤 행동이 호출됐는지를 기록
spy실제 객체와 똑같이 행동하며, 모든 행동 호출을 기록
  • dummy 는 아무런 동작을 하지 않는다.
  • stub 은 미리 준비된 값을 반환 하는 대역 객체다. 테스가 원하는 방향으로 동작할 수 있게 한다.
    • 미리 준비한 값을 그대로 반환해서 고연산 작업이 실제로 실행되지 않게한다.
    • 테스트를 결정적 으로 만들어 준다.
  • mock 은 메서드 호출 및 상호 작용을 기록하고, 어떻게,어떤 상호 작용이 일어났는지 기록한다.
  • 상태 기반 검증 : 테스트 검증에 대상의 상태를 사용
  • 행위 기반 검증(상호 작용 테스트) ** : 테스트 대상, 협력 객체, 협력 시스템의 메서드 호출 여부를 확인
  • 테스트를 회귀 버그를 방지하는 목적만이 아닌 좋은 설계를 위해 테스트를 사용할 수 있다.
  • 테스트 가능성
    • 테스트하기 쉬운 코드일수록 테스트 가능성이 높다.
    • 테스트 하기 쉬운 코드 일수록 좋은 설계일 가능성이 높다.
  • 숨겨진 입력을 제거하라
    • 숨겨진 입력이나 숨겨진 의존성은 테스트하기 어렵게 만든다.
    • 숨겨진 입력을 외부로 드러내어 테스트 가능한 코드로 변경 가능하다.
    • 매개변수에 입력을 받는 코드로 변경한다.
  • 숨겨진 출력을 제거하라
    • 숨겨진 입/출력은 테스트 가능성을 낮춘다.
    • 숨겨진 출력은 반환 값 이외에 존재하는 모든 부수적인 출력을 의미한다. (side effect)
  • 테스트와 설계
    • 테스트는 회귀 버그 방지 뿐 아니라 시스템을 좋은 설계로 발전 시키기 위해 수행한다.
    • 테스트와 좋은 소프트웨어 설계는 같은 목표를 공유한다.
      • 모듈을 분해하고 독립적으로 개발될 수 있게 하는 것을 추구
      • 모듈화, 재사용성을 높인다.
    • 테스트 하기 어려운 코드는 좋은 설계 원칙을 적용해 테스트 하기 쉽게 만든다.
    • 언떤 방식이 좋은 설계 인지 헷갈린다면 테스트하기 쉬운 코드를 선택한다.
    • 좋은 설계의 대표인 SOLID는 테스트 코드를 통해 유도할 수 있다.
  • SRP
    • 테스트 작성함으로써 의존성을 고민하게된다.
    • 불필요한 의존성을 줄이기 위해 컴포넌트를 분리하는데, 이로써 단일 책임원칙을 지킬 수 있게됐다.
  • ISP
    • 테스트 할때 테스트 하고 싶은 것에만 관심을 가지고 싶다.
    • 그러나, 인터페이스 분리 원칙을 위배한 코드는 대역 객체를 만들기 위해 테스트에 필요하지 않은 다른 함수들도 구현해야한다.
    • 이때, 테스트가 인터페이스를 분리하라는 신호를 보내게된다.
    • 인터페이스를 분리해 테스트 하기 쉬운 코드로 변경하며, 인테페이스 분리원칙을 지킬 수 있다.
  • OCP
    • 테스트 코드가 유연성과 확장성을 평가하는 기준이 될 수 있다.
    • 테스트는 배포환경과 다른 새로운 요구사항에 대처하는 곳이기 때문에 개발자는 시스템이 배포환경과 테스트 환경에서도 원활하게 실행될 수 있게 만들어야 한다.
    • 그결과 코드가 유연해진다.
  • DIP
    • 추상화를 통해 유연성을 추구한다.
    • 마찬가지로 테스트를 고민하다보면 자연스레 DIP 를 지키게 된다.
  • LSP
    • 리스코프 치환 역시 시스템이 유지하고 싶은 상태 중 하나이기에 테스트해야한다.
    • 파생 크래스가 기본클래스의 계약을 깨트린다는 것이 리스코프 치환 원칙을 어긴다는 의미이다.

public class RectangleTest extends RectangleLiskovTest{
@Override
public Rectangle createSystemUnderTest(){
return new Rectangle(10,5);
}
@Override
public long getSystemUnderTestArea(){
return 50;
}
}

- 위와같이 템플릿 메서드 패턴을 적용해 상위 테스트를 통해 파생 클래스의 테스트를 수행할 수 있다.



- **TDD**
	- red (테스트 코드 작성), green(기능 구현), blue(리팩터링, 성능 개선) 로 구분된다.
	- TDD 는 요구사항이 명확하지 않은 프로젝트에서 적합하지 못하다. 
	- 은탄환은 존재하지 않는다.
- **BDD**
	- TDD 에 사용자 행동이란 가치를 더함
	- 행동 명세와 같은 요구사항을 먼저 만들고 테스트로 표현될 수 있게 한다.
	- **테스트가 곧 요구사항 문서이자 기획 문서**가 된다.
	- **BDD 테스트 단위가 사용자의 행동**이며, 이에 맞춰 애플리케이션을 설계한다.
	- **given-when-then** 으로 테스트케이스를 작성
	- TDD 는 객체지향적 코드가 아니다.
	- BDD 는 TDD 에 객체지향적인 설계를 얻기위해 DDD를 얹은 것이다.
	- BDD 는 사용자 스토리 기반의 요구사항과 기획 문서를 바탕으로 테스트를 작성한다.
	- 행동 명세(사용자 스토리 기반의 요구사항)는 다음과 같다.
		- 시나리오 #1
			- given
			- when
			- then
