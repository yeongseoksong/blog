1.1.3 SQL 옵티마이저

  1. 쿼리를 수행하는 데 후보군이 될만한 실행계획 생성
  2. 데이터 딕셔너리에 저장 해둔 오브젝트 및 시스템 통계 정보로 실행계획의 예상 비용 산정
  3. 최저 비용의 실행계획 선택

1.1.4 실행계획과 비용

  • 옵티마이저는 네비게이션 알고리즘과 흡사
  • DBMS 는 실행계획으로 실행경로를 미리 볼 수 있다.
  • 비용기반으로 싱행계획을 선택하는데, 비용은 쿼리를 수행하는 동안 발생할 예상 I/O 횟수 또는 예상 소요 시간을 표현한 값이다.
  • 실행 계획은 예상 소요 시간으로 실제와는 다를 수 있다.

1.1.5 옵티마이저 힌트

  • /+ INDEX(A 고객_PK) /
  • 옵티마이저는 보편적으로 좋은 선택을 하지만 항상 최선은 아니다.
  • 옵티마이저 힌트를 통해 데아터 액세스 경로를 명시해 줄 수 있다.

1.2 SQL 공유 및 재사용

1.2.1 소프트 파싱 vs 하드 파싱

  • 라이브러리 캐시 : SQL 파싱, 최적화, 로우 소스 생성 과정을 거쳐 생성된 내부 프로시저를 캐싱 하는 공간
  • SGA (system global area) : 서버 프로세스와 백그라운드 프로세스가 공통으로 엑세스하는 데이터와 제어구조를 캐싱하는 메모리 공간
  • 소프트 파싱 : SQL 을 라이브러리 캐시 에서 찾아 곧바로 실행 단계로 넘어 가는 것
  • 하드 파싱 : 캐시에서 SQL 을 찾지 못해 최적화 및 로우 소스 생성 단계를 모두 거치는 것
  • 옵티마이저가 경로 설정에 사용하는 정보
    • 테이블, 칼럼, 인덱스 구조
    • 오브젝트 통계 (테이블, 인덱스, 히스토그램)
    • 시스템 통계 (cpu, sing block i/o 속도)
    • 옵티마이저 관련 파라미터
  • DB의 처리과정은 대부분 I/O 작업 이지만, 하드 파싱은 CPU 를 많이 소비하는 작업 중 하나이다.
    • 그렇기 많은 자원을 소비해(하드 파싱) 생성한 프로시저를 라이브러리 캐시에 저장 한다.

1.2.2 바인드 변수의 중요성

  • SQL 은 함수/프로시저 등과 다르게 이름이 필요하지 않다.
  • SQL 텍스트 전체를 이름처럼 사용할 수 있기 때문이다.
  • 라이브러리 캐시에 SQL 을 저장 할 때는 키 값으로 SQL 그 자체를 사용한다.
  • 파라미터가 필요한 SQL 은 파라미터가 대입된 SQL 전부터 라이브러리 캐시에 존재하게 된다. (매번 하드 파싱이 일어난다.)
  • 와 같이 바인드 변수 를 사용하면 라이브러리 캐시에는 하나의 SQL 만 존재하게 된다.

1.3 데이터 저장 구조 및 I/O 메커니즘

1.3.1 SQL이 느린이유

  • SQL 이 느린 이유는 대개 디스크 I/O 때문이다.
  • 프로세스는 디스크 I/O 시에 대기 큐에 들어가게 된다.
  • I/O Call 이 완료되면 다시 Ready 큐에 들어간 후 스케줄링에 의해 CPU에 할당된다.
  • I/O Call 초당 100블록 ~ 1000 블록 (SSD) 을 읽는데 어떤 SQL 이 10,000 블록을 읽는다면 10초 이상 기다려야 한다.
  • 수 많은 프로세스에서 I/O Call 을 요청 하게 되면 디스크 경합이 심해지고 대기 시간이 매우 길어지게 된다.

1.3.2 데이터 베이스 저장 구조

  • 데이터를 저장하려면 테이블 스페이스를 먼저 생성해야한다.
  • 테이블 스페이스는 세그먼트를 담는 컨테이너로 여러개의 데이터 파일 (디스크 상의 물리적인 OS 파일)로 구성된다.
  • 세그먼트는 테이블, 인덱스 처럼 데이터 저장공간이 필요한 오브젝트다.
    • 세그먼트는 여러 익스텐트로 구성된다.
    • 테이블, 인덱스는 하나의 세그먼트로 구성된다.
    • 만약, 파티션 테이블이라면 각 파티션이 하나의 세그먼트가 된다.
  • 익스텐트 공간을 확장하는 단위로, 데이터를 입력하다가 공간이 부족해지면 테이블 스페이스 부터 익스텐트를 추가로 할당 받는다.
    • 익스텐트는 연속된 여러 블록으로 구성된다.
    • 익스텐트 하나는 하나의 테이블이 독점한다.
    • 익스텐트 단위로 공간을 확장하지만 실제 레코드를 저장하는 공간은 블록(페이지)다.
  • 블록 실제 레코드가 저장되는 공간이고 한 블록은 하나의 테이블이 독점한다.
    • 한 블록에 저장된 레코드는 모두 같은 테이블 레코드이다.
  • 세그먼트에 할당된 모든 익스텐트가 다른 데이터 파일에 위치할 확률이 매우 높다. 하나의 테이블 스페이스를 여러 데이터 파일로 분산 저장해 DBMS 가 파일 경합을 줄인다.
  • 테이블 스페이스 > 세그먼트 > 익스텐트 > 블록
    • 데이터파일은 디스크 상의 물리적인 OS 파일이다.

1.3.2 블록 단위 I/O

  • 데이터베이스에서 데이터를 읽고 쓰는 단위는 블록
  • 레코드르 하나 읽고 싶어도 해당 블록을 통째로 읽어야 한다.
  • 인덱스 또한 블록 단위로 데이터를 읽고 쓴다.

1.3.4 시퀀셜 엑세스 vs 랜덤 엑세스

  • 테이블 혹은 인덱스 블록을 엑세서 하는 방식
    • 시퀀셜
      • 논리적, 물리적 연결된 순서에 따라 차례로 블록을 읽는것을 의미한다.
      • 인덱스 리프 노드를 스캔해 블록을 논리적 순서대로 순차적으로 읽는다.
      • 테이블 블록은 서로 논리적 연결 고리가 없다.
        • 오라클은 한 세그먼트의 익스텐트 목록을 세그먼트 헤더에 익스텐트 맵으로 저장한다.
        • 익스텐트 맵에는 각 익스텐트의 첫번 째 블록의 주소를 저장한다.
        • full table scan 은 읽어야 할 익스텐트 목록을 익스텐트 맵에서 얻고, 각 익스텐트의 첫번째 블록 부터 연속해서 저장된 블록을 순서대로 읽는 것이다.
    • 랜덤
      • 논리적, 물리적 순서를 따르지 않고 레코드 하나를 읽기 위해 한 블록씩 접근 하는 방식

1.3.5 논리적 I/O vs 물리적 I/O

  • DB 버퍼 캐시
    • 데이터를 캐싱 하는 영역으로 SGA 의 구성요소 중 하나
    • 캐시 히트 시에 디스크 I/O 로 인해 프로세스가 sleep 되는 것을 막아준다.
  • 논리적 I/O
    • SQL 처리 과정에서 발생한 총 블록 I/O
    • 일반적으로 메모리상 버퍼 캐시를 경유 하므로 메모리 I/O 가 곧 논리적 I/O
  • 물리적 I/O
    • 디스크에 발생한 블록 I/O
    • 논리적 블록 I/O 중 일부를 물리적 I/O 함 (캐시 미스)
  • 버퍼캐시 히트율
